**1. Does A + B settle it?** Not fully — they settle the *client process* question and strongly implicate a *shared upstream hop*, but they don't localize which hop. A closes round 1's loophole decisively: a blocked reader would show multi-second loopback latencies and gaps; you saw ≤3 ms handlers and ~5 s idle gaps, i.e., a healthy event loop that simply had no stream bytes to read. B's cross-process, cross-model, same-wall-clock correlation rules out anything per-process or per-model. The strongest surviving alternative: the stall sits on the shared path **below the gateway's application logic but above the client's socket** — local system proxy/VPN/DNS, the gateway's TLS edge or load balancer accepting the connection while its upstream queue is stuck, or a network-path packet-loss/retransmit burst. From the client all of these look identical: request written, socket open, silence, free loop. Ruling measurement: during a stall, (i) a concurrent raw `curl -N --trace-time` from the same machine to the same gateway/model, and (ii) pcap or socket stats (retransmit counters, per-socket RTT) on the stream connection. If curl stalls identically with "request written, zero bytes back, no retransmit storm," the gateway-and-behind bucket is confirmed and the client is fully excluded; if curl is clean, a machine-shared layer (proxy config, shared credential refresh) is implicated instead.

**2. Cheapest artefact for the gateway owner.** One incident-timeline file, three rows: per process — UTC request-start timestamp, model, **gateway request-id from response headers if echoed**, observed first-byte/stream-event times, hole duration (110 s / ~30 s-error / 161 s). The overlapping wall-clock window across three independent sessions and two models is the actionable core — it converts "that model was slow" into "a shared capacity/queueing/failover event at time T" — and the request-ids make it greppable in their access logs. Add one pre-emptive line: "client event loops verified healthy throughout (56 loopback reqs, ≤3 ms)." It needs no new instrumentation; a raw curl capture is valuable but requires catching a live stall, so it's the follow-up artefact, not the first.

**3. Remaining client-side multi-process stall path?** Yes, one narrow family survives A + B: serialization on a **shared on-machine resource sitting between socket arrival and chunk delivery**. Prime suspect: the shared 10 GB session SQLite file — a long write transaction, WAL checkpoint, or fsync storm in one process blocks the other two's event-persistence writes; if first-chunk delivery is gated behind persistence (or shares a worker pool), all three stall simultaneously and model-independently while the event loop stays free, because async persistence doesn't freeze the loop. A doesn't exonerate this: ≤3 ms handlers prove loop health, not that the delivery path bypasses the DB. (Caveat: if any of those 56 handlers read the session DB, this hypothesis weakens sharply.) Weaker residuals: any other shared file lock in the state dir; shared credential refresh — but that predicts stalls at connection setup, not P1's mid-stream +9.1 s→+119.7 s hole. Ruling measurement: dual timestamps per chunk (`socket data arrived` vs `delivered past the adapter`) plus SQLite busy/lock counters or WAL-file-size monitoring during the next stall.

**4. The one measurement before closing.** Split TTFT at the client into two timestamps on the same first chunk: **t1 = first response bytes on the socket, t2 = first chunk delivered past the adapter to the consumer**, captured during the next stall. That single split simultaneously closes the last client-side loophole (SQLite/backpressure serialization, Q3) and — if t1 also shows the hole — upgrades "gateway TTFT" from inference to socket-level fact. Cheap rider: fire the raw curl probe from Q1 in the same window.
