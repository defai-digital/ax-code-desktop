Selective WebAssembly in AX Code Desktop is not justified by this evidence. The only gated experiment is enabling Pierre’s existing in-worker `shiki-wasm` highlighter. Every other kernel here should stay JavaScript, stay in its current worker, or stay outside Desktop.

## Evidence classes

**Source facts**

- `DiffWorkerProvider.createWorkerPool` forces `preferredHighlighter: "shiki-js"` and comments that packaged `app://` workers disallow WebAssembly compilation. Pools are small: unified is `poolSize: 1`, `totalASTLRUCacheSize: 24`, `lineDiffType: "none"`; split is `poolSize: 2`, cache `56`, `lineDiffType: "word-alt"`.
- The markdown worker (`createMarkdownWorkerParser`, `createMarkdownWorkerResponder`) parses with `unified` + `remark-parse` + `remark-gfm` + `remark-math`, reuses a live prefix, copies completed UTF-16 text with `split("").join("")`, reparses the live tail, and returns only an unacknowledged suffix.
- `PreparedMarkdown` installs that MDAST through `remarkPreparsed`, then still runs React Markdown, GFM, math, and KaTeX. `MarkdownRenderBoundary` renders raw text after a render throw.
- `scoreByFuzzyQuery` short-circuits prefix and substring hits, and constructs a new `Fuse` only for the remainder (`threshold: 0.3`, `distance: 100`, `minMatchCharLength: 2`).
- `createMermaidRenderer` uses one worker, a queue, an SVG cache, abort, and a timeout that calls `terminate()`. `renderOfficialMermaid` lays out in a hidden DOM node.
- `WikiGraphPanel.openViewer` calls `desktop_open_wiki_viewer`. It has no local layout kernel.
- `haveEquivalentPartSnapshots` equates parts with `JSON.stringify(part)`.

**Operator facts supplied with the excerpts**

- Production CSP allows `wasm-unsafe-eval` and does not rely on `unsafe-eval`. The Pierre CSP comment is stale relative to current document headers. Packaged worker instantiation is still untested.
- `@pierre/diffs` 1.2.11 can select `shiki-wasm` through `createOnigurumaEngine(import(shiki/wasm))`.
- `PierreDiffViewer.tsx` stops highlighting above `500 * 1024` JavaScript string length, which is UTF-16 code units.
- Markdown admission is 16,384 code units, with a 1,000,000 cap. Those checks are outside the pasted parser.
- Streaming coalescing, incremental turn projections, retention bounds, and worker recovery already exist.
- AkiTTY Web 0.5.2 is the pinned import of akitty `4daf16ce6cbb394a325b0f706779600bba045a83`. Ghostty’s VT parser is already WASM inside that import.
- Desktop owns UI and control plane. Runtime owns repository intelligence. AX Agent owns durable runs. AX Trust owns credentials and policy.

**Hypotheses**

- Oniguruma may spend less CPU than Shiki’s JS engine on hard grammars, and it may also increase cold-start and grammar memory. Direction is unknown.
- MDAST structured clone, React/HAST, and KaTeX may dominate `parser.parse`. Unknown.
- `JSON.stringify` part equality and per-keystroke `Fuse` construction may stall some sessions. Call sites and sizes are absent.
- Split view is configured as the heavier diff mode. That is a design signal, not a profile.

**Uncertainty from sampling**

`workerFactory`, `PRELOAD_LANGS`, pool failure behavior, Mermaid’s queue/fallback policy after line 65, the official renderer before line 65, Fuse call sites, and the rest of `materialization.ts` were not in the excerpts. Electron/Chromium build and worker CSP response headers were not shown.

| --- | --- | --- |
| 1 | Pierre highlighter, in worker | Only experiment. Enable upstream `shiki-wasm` after the gates below. |
| 2 | Markdown `parseSyntax` | Leave on remark in the worker. |
| 3 | `scoreByFuzzyQuery` | Leave in JS. Reuse a Fuse index only if a palette profile shows a stall. |
| 4 | Mermaid layout | Leave on the current single worker and DOM official path. |
| 5 | Wiki viewer | Runtime-owned. |

| 8 | KaTeX, HAST, React render | DOM and component work. |

### 1. Pierre `shiki-wasm` — experiment, not a new kernel

`createWorkerPool` already runs highlighting off the renderer, with AST LRU caps of 24 and 56. The WASM Oniguruma engine in `@pierre/diffs` 1.2.11 stays inside that worker if Pierre applies tokens there. Desktop would change a preference from `shiki-js` to `shiki-wasm`, package `shiki/wasm`, and prove the worker can compile it.

That is the only candidate whose ABI stays the current worker boundary, whose implementation is upstream, and whose stated blocker is a comment the operator says is stale. It still needs a packaged-worker test. A missing fallback would make highlighting less stable than `shiki-js`.

Files at or above `500 * 1024` JS characters already skip highlighting in `PierreDiffViewer`. WASM does not change that path. Benchmarks have to include both sides of that gate, in UTF-16 length and UTF-8 bytes.

Grammar output can diverge where Oniguruma accepts constructs the JS regex engine approximates. `lineDiffType: "word-alt"` on the split pool must be part of the parity set. Pool sizes should stay 1 and 2.

### 2. Markdown parser — no migration

`markdownWorkerParser.ts` is already an incremental worker protocol. Live reuse requires the same `baseKey` and `request.text.startsWith(previous.text)`. Stable full blocks keep object identity. The responder emits a suffix only when `ownerId`, `baseKey`, and `baseRevision` match. The live tail is parsed again and its old AST is dropped. Finalization clears the cache.

`PreparedMarkdown` depends on a remark MDAST `Root`. `remarkPreparsed` replaces `this.parser` with that tree. A cmark-class WASM parser would still have to be rebuilt into MDAST, then cloned to the renderer, while GFM, math, URL filtering, and KaTeX remain in JS. The transfer can erase a parse win. This cost is unmeasured.

`split("").join("")` deliberately copies UTF-16 units so a sliced string does not retain a streaming snapshot and so an unfinished surrogate survives. A UTF-8 WASM boundary replaces lone surrogates. That changes live-tail behavior.

The cited stack overflow is in React Markdown render. `MarkdownRenderBoundary` already turns that into raw text. Moving parse into WASM leaves that render path in JS.

Admission at 16,384 code units and the 1,000,000 cap already bound input. Those limits are the stability control.

### 3. Fuzzy ranking — no migration

`scoreByFuzzyQuery` is a UI ranker: prefix score `-1`, substring score `idx / 1000`, then Fuse. Corpus size is not in the excerpt. Command palettes are often small enough that a WASM call and string copy dominate. A WASM index would also change ranking unless it reproduces Fuse scores.

Repository-wide fuzzy search belongs to the AX Code runtime. A renderer WASM index would be a second search implementation.

If a later profile shows a main-thread stall, the first change is to reuse one Fuse index across keystrokes while `items` are unchanged. That alternative is unmeasured too.

### 4. Mermaid — no migration

`createMermaidRenderer` already serializes layout, caches SVG text, and bounds a stuck job with timeout plus `worker.terminate()`. `renderOfficialMermaid` calls `mermaid.render` into a DOM container. Diagram layout that needs DOM does not become a numeric WASM kernel. SVG sanitization goes through `sanitizeMermaidSvg` before display; a replacement renderer would have to preserve that.

The worker/official selection policy is past the excerpt cut, so the fallback’s exact trigger is unknown. The visible design is already bounded recovery.

### 5–8. No-go areas

**Wiki.** `WikiGraphPanel` opens a runtime-exported viewer and queues runtime refresh. A Desktop layout kernel would duplicate runtime ownership.

**Terminal.** Ghostty VT is already the WASM parser inside AkiTTY Web 0.5.2. Desktop should keep the pin and upgrade through akitty `4daf16ce`, rather than wrapping or replacing VT.

**Materialization.** `partSnapshotKey` walks SDK part objects. Those graphs carry merge, streaming `text`/`output`, and ordering semantics (`mergeMessages`, `keepCompletedMessageOnMerge`, `shouldPreserveExistingPart`, `sortPartsById`). Shipping them into linear memory costs another serialization at least as heavy as the current `JSON.stringify`. A mismatch is a transcript bug. Incremental JS projections are already the intended design.

**Render and trust boundaries.** KaTeX and React Markdown emit DOM. Credentials, policy, durable agent runs, and coding tools stay in AX Trust, AX Agent, and the AX Code runtime. Desktop WASM must not become a second runtime or a credential store.

## ABI, strings, and ASTs

JavaScript strings are UTF-16. WASM linear memory is normally UTF-8. Each crossing copies. Markdown, diffs, and Mermaid are string-shaped, so the copy is the payload.

Current crossings, from the code:

- Markdown responses already structured-clone `ParsedMarkdownBlock` values, including `tree`. `stablePrefixCount` is what keeps that clone small. A WASM full reparse that returns a new tree every flush removes that identity protocol.
- Building MDAST from WASM means either JS object calls out of the module, or a serialized tree decoded back into remark’s shape. Both add a second representation.
- Diff token ASTs are implied to remain in the Pierre worker by `WorkerPoolManager` and `totalASTLRUCacheSize`. That is why Oniguruma is viable: the extra copy is worker-local, into the module and back to JS tokens, and the renderer boundary stays as it is. Confirm that in Pierre before shipping. The pool implementation is not in these excerpts.
- Mermaid already transfers source in and SVG text out, then caches it. Another intermediate tree adds copies.
- Fuzzy search would copy candidate strings per query, or keep a WASM index whose lifetime must follow UI list identity.
- Part snapshots are object graphs. `JSON.stringify` is already the walk. WASM does not remove it.

Lone surrogates are the concrete compatibility hazard. The markdown worker copies UTF-16 units because streaming snapshots can split a pair. UTF-8 conversion is lossy there.

## Semantics that a port would have to preserve

- Remark MDAST plus GFM plus math, including reference-definition rewrites that the responder treats as identity breaks.
- Live versus full blocks, prefix reuse, and “tail is never retained.”
- UTF-16 code-unit limits: markdown 16,384 / 1,000,000 and diff highlighting `500 * 1024`. A byte-length WASM gate would change when work is refused.
- Fuse order: prefix, then substring, then fuzzy score. Empty query returns every item with score 0.
- Mermaid version behavior and sanitized SVG.
- Shiki token classes and `word-alt` hunks if the highlighter engine changes.
- Part merge results versus the SDK. Equality has to stay behavioral even if `JSON.stringify` is later narrowed.

Visual or ranking drift is a product change and needs an explicit accept list. Transcript merge drift does not.

## Bounded failure recovery

Keep recovery outside the module and prefer `terminate()` on a worker over a main-thread trap.

Existing bounds to keep:

- Diff pools already return `undefined` when `window` is missing. Highlighting already degrades by file size.
- Markdown render throws become raw text in `MarkdownRenderBoundary`, which resets when `raw` changes.
- Mermaid maps construct failure to `MermaidRenderError("unavailable")`, timeout to `"timeout"` plus `terminate()`, and abort to the same teardown.

WASM adds compile failure, bad MIME, missing asset, and `WebAssembly.RuntimeError`. For the Pierre experiment, those must fall back to `shiki-js` or to unhighlighted text, and must recreate only that pool. A trap on the renderer thread would sit outside `MarkdownRenderBoundary` if it happens before React’s boundary. Keep any new module in a worker.

Multithreaded WASM and `SharedArrayBuffer` are out of scope. The shown designs are single-threaded pools and one Mermaid worker. Threads would add cross-origin isolation and make `terminate()` a weaker recovery story.

## Deployment and CSP

Document CSP already has the token Shiki WASM needs: `wasm-unsafe-eval`. `unsafe-eval` is not required for `WebAssembly.instantiate`.

The open deployment check is the worker, not the document. `DiffWorkerProvider` still records the old assumption that packaged `app://` workers cannot compile WASM. Worker scripts can be a separate response. The experiment needs the packaged worker’s own CSP to compile `shiki/wasm`, with `application/wasm` or an `arrayBuffer` fallback if `instantiateStreaming` rejects the MIME type.

Vite must emit the WASM asset into the packaged shell. A successful dev-server compile does not prove the `app://` path. Supply chain stays on the existing `@pierre/diffs` 1.2.11 pin and its `shiki/wasm` dependency. A Desktop-built WASM toolchain would be a new release surface and is not warranted.

A native addon in the Electron shell is a worse fit for these UI kernels: it ties the UI to the Electron ABI, signing, and universal builds, and it pulls control-plane work toward a second runtime. Heavy repository work belongs in the AX Code runtime process the desktop already launches.

## Alternatives, in the order to try them

1. **Measure packaged builds first.** Worker time, main-thread long tasks, cold highlighter start, heap peak. No migration without that baseline.
2. **Keep the incremental JS already present.** Markdown prefix identity, suffix responses, slice detachment, diff size degradation, Mermaid single-flight, session projections.
3. **Use the workers already present.** Diff pool, markdown worker, Mermaid worker. Add WASM only inside a worker that a profile shows is CPU-bound after those bounds.
4. **Batch only where a trace shows a storm.** Mermaid is already queued. Diff pool sizes are already 1 and 2. Streaming coalescing is already part of the product.
5. **Call the runtime for runtime work.** Wiki, repository search, and coding intelligence stay there. Terminal stays the AkiTTY pin.
6. **Then, and only then, try `shiki-wasm`.** One variable. Leave `shiki-js` as the fallback.

## Benchmark gates

Proposed decision rules, not results. Use a packaged renderer under production CSP. jsdom microbenchmarks do not see worker CSP or WASM compile. Report median, p95, and worst over enough runs that the intervals are visible. Record UTF-16 length and UTF-8 bytes.

**Ship `shiki-wasm` only if all of these hold**

1. **CSP.** Packaged `app://` and web workers compile `shiki/wasm` with `wasm-unsafe-eval` only. A removed or corrupt `.wasm` file falls back to `shiki-js` or plain text. The diff UI stays up. Both unified and split pools recover.
2. **Parity.** For every preloaded language, token classes or rendered HTML match `shiki-js`, or the difference is written down and accepted. Split `word-alt` fixtures stay stable. The `500 * 1024` JS-length cutoff still disables highlighting on the same strings.
3. **Time.** On a fixed corpus under that cutoff, worker p95 is within noise of `shiki-js`, or better by a threshold agreed before the run. Suggested rule: require at least 20% p95 reduction with non-overlapping intervals; otherwise keep JS. Cold compile must not push first highlighted frame past a budget also set before the run. Over-cutoff files should be unchanged.
4. **Memory.** Peak worker heap stays within a pre-set delta of the JS engine. Grammar modules must not grow with the AST LRU. Caps stay 24 and 56, pools stay 1 and 2.
5. **Kill.** Any CSP failure, any unaccepted grammar drift, or a gain inside noise means the preference stays `shiki-js`.

**Do not open another WASM port unless a profile passes these first**

- Markdown: `parser.parse` is the majority of worker time on admitted inputs after prefix reuse, and HAST/React/KaTeX are separately smaller. Fixtures must deep-equal remark MDAST, including GFM, math, streaming prefixes, and lone surrogates. Suffix identity and `stablePrefixCount` must stay. AST bytes on the wire must not increase. This bar is why a replacement should not be scheduled now.
- Fuzzy: a realistic palette produces a main-thread task over 16 ms, and a reused JS Fuse index still misses a pre-set budget in that same harness. Ranking permutation against current scores needs an explicit accept list. Large file corpora go to the runtime instead.
- Mermaid: a headless layout would have to match current SVG closely enough for review and still pass `sanitizeMermaidSvg`, with the same timeout and `terminate()` behavior. Upstream Mermaid remains the owner of that engine.

## Decision

Leave the architecture as it is. Schedule one packaged experiment for Pierre `shiki-wasm` versus today’s `shiki-js`, behind the gates above, with `shiki-js` left in place as fallback. Do not add a Desktop WASM markdown parser, fuzzy index, Mermaid renderer, wiki layout, terminal parser, or session-materialization kernel. No speedup is claimed.
