# AX Code Desktop 7.26.1 candidate verification

The candidate starts from `11eae3e53d7952112ec91911f14de73cdc1d39a0` in an isolated worktree and preserves the primary checkout. It consumes signed AX Code runtime 7.26.0 and exact published SDK 2.6.22.

## Reproduced fixes

- A downloaded installer can still refuse to start. Previously Desktop stopped the server/runtime, disposed launch animations and set `isQuitting` before calling the installer; failure left the open app unusable. Installation now leaves services running until the app's actual quit coordinator performs cleanup. Thrown errors, synchronous wrapper errors and native staging errors finish promptly, temporary listeners are removed, and concurrent IPC requests share one attempt.
- An ordinary app quit was accepted as evidence that update installation had started. The old helper was reproduced returning true after only an ordinary `before-quit`. The observer now listens to Electron's native `before-quit-for-update`, which the pinned electron-updater uses on both its BaseUpdater and MacUpdater paths. An install request is refused once normal quit cleanup has begun.
- A mutable PartMap retained ownership of buckets shared with a newly forked child. A later parent overwrite, insertion or deletion could silently change a published child while leaving its stored count unchanged. Forking now relinquishes parent bucket ownership so both sides copy before writing. Published-parent streaming updates retain their existing constant bucket-table copying cost.

Focused regressions reproduced snapshot corruption and the ordinary-quit false positive before the fixes. Tests cover colliding IDs, repeated forks, untouched buckets in published copies, synchronous update signals, emitted/thrown errors, listener cleanup, silent refusal, shared install requests, and integration with the actual quit coordinator.

## Independent review

Muse completed its initial snapshot review with exit code 0 and supplied the two updater findings above. Both were reproduced and fixed. Its second review of the proposed fix confirmed those defects were fixed. Raw completed review text and dispositions are recorded in `.internal/reviews/release-7.26.1/`.

The follow-up review exposed a candidate regression: a wrapper error from a background check during native staging could falsely end the observer. Regression tests reproduced this, and the final observer now listens to wrapper errors only during the synchronous installer call while continuing to observe native staging errors. The first candidate `38c7ff3f1a98aa769e58948629ba6cdd72065e8e` was superseded; its passing CI/CodeQL and partial Linux receipts are not reused. Its remaining signing run was cancelled. A further completed Muse review confirmed the background-error lead addressed in the stated Mac production wiring and found no concrete regression in its scope.

The follow-up review also raised two limits of existing lifecycle policy. A 30-second observation deadline does not cancel a native install already staging, so a late native install can still quit after a negative start observation. This deadline and lack of native cancellation predate this patch; the patch leaves services available while waiting and makes no cancellation guarantee. A hanging service shutdown can block quitting, as it could when shutdown was awaited before launching the installer. Neither concern establishes a regression in the reproduced fixes or justifies inventing platform cancellation or force-exit policy here. These limits remain recorded rather than being counted as fixed.

Grok completed a bounded PartMap/batching/materialization snapshot review with exit code 0, one turn, and zero tool calls. It independently identified the reproduced parent-ownership defect. Its proposed transactional batch rollback was not adopted: existing tests deliberately require isolation of malformed events while preserving valid deltas, production dispatch separates non-delta barriers, and an observer callback failure does not invalidate an already reduced delta. Discarding valid streaming data would change that contract and lose updates.
