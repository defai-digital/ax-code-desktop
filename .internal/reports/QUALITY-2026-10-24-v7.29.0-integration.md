## Confirmed defects and repairs

### Full runtime verification before use

Claude Code identified a regression introduced after public v7.28.7: a writable integrity receipt caused a warm launch to hash only two startup files and execute the runtime while the complete trusted-manifest scan ran in the background. A modified sidecar could execute first, including code that restored itself before background hashing.

Every packaged launch now awaits the complete asynchronous trusted-manifest verification before either the runtime or web server starts. Receipt fields only describe prior metadata; they never authorize skipping hashes. The partial startup-file shortcut and its background teardown callback are removed. The original immutable ASAR manifest, signature policy and runtime ownership remain in place. This restores the prelaunch integrity gate; it does not claim atomic filesystem immutability between verification and execution.

Receipt writes or cleanup could also reject an otherwise valid runtime or replace the original integrity error. Receipt I/O is now best effort, emits bounded generic warnings on write/cleanup failure, and never changes the full scan's result. An invalid runtime still rejects before launch.

Four new/updated behavioral regressions failed against the old warm path and passed after the repair: a pending full scan cannot open the launch gate; matching metadata cannot authorize tampered sidecar execution; receipt write failure on either hit or miss does not reject a valid runtime; receipt cleanup failure preserves the original integrity error. The obsolete partial-descriptor tests were replaced because that shortcut no longer exists; complete verifier tests remain.

### Portable WebMCP checker execution

The project-browser task journey assumed pnpm was a JavaScript file. Hosted standalone binaries and some shims failed before exercising the checker. The journey now runs the existing webmcp-check.mjs directly with the current Node executable, without a shell or pnpm discovery. Behavioral child-process tests cover an empty PATH, paths with spaces, JSON quotes and backslashes, checker failure status/diagnostics, launch failure, and split UTF-8 output. Claude's follow-up caught the UTF-8 decoding issue; the runner now uses streaming UTF-8 decoding on both pipes.

### Bounded Apple ticket lookup recovery

The unpublished e68e7915 candidate failed macOS qualification on three same-source attempts. The first reached final reinstall after fresh/upgrade ASAR smokes passed, then ticket validation failed. The next two logs explicitly show Apple CloudKit connection loss (-1005/error 68), during app stapling and after an accepted DMG notarization and successful staple. No public tag, release or download alias was created from that candidate.

The existing CI retry helper now wraps macOS package/staple recovery and DMG ticket validation. Native app ticket validation uses the same helper. It defaults to three attempts with 20/40-second backoff, preserves the exact validation command and app argument, returns success only after the command succeeds, and propagates terminal failure. Codesign, spctl, pinned identity, native continuity assertions, the existing ten-minute command timeout and job timeout remain unchanged. No invalid ticket is accepted. Complete source-bound CI and signed five-target/native qualification must rerun for the new commit; earlier candidate receipts are historical only.

Real child-process fixtures cover recovery after two failed lookups, failure after all three attempts, and stopping on the first success, including an app path with spaces. Restoring the old one-shot call causes two of these cases to fail; all 14 native qualification tests pass with the retry wrapper. Both Grok CLI and Claude Code CLI completed a read-only follow-up with exit 0 / end_turn and no actionable findings. Their scopes also reconfirm the earlier integrity and UTF-8 fixes. Successful native retry warnings remain captured by the existing command wrapper; this change does not claim per-attempt success telemetry or independent descendant-process cleanup beyond the hosted job boundary.

### Revocation isolation test deadline

A complete-suite rerun exposed a test fixture with a two-second navigation deadline, exactly equal to the 1,500 ms reply reserve plus the 500 ms minimum load budget. Any dispatch delay makes that request correctly time out. The session-revocation isolation case now keeps the navigation fixture's normal deadline instead of overriding it to this boundary. Its one-second completion assertion, production timing policy and dedicated deadline regressions are unchanged. This repairs an unrelated timing assumption without weakening the isolation assertion.

### Disproved review lead

The browser navigation deadline subtraction cannot receive a missing or nonfinite deadline through its runtime request entry: Number.isFinite(request.deadline) is required before dispatch. This suspicion did not justify a source change. Removing the background integrity shortcut also removes the reported background-scan/startup race.
