## Verdict

Ship the smallest change first: **block-only lexing inside `buildLiveMarkdownBlocks`**, gated by attribution and golden parity. Reject **block batching** and a **handwritten fence parser** in this pass. Keep Shiki on JS. Do not integrate the sibling `@ax-code/diff-wasm` pilot: it exposes only duplicate comparison, not preview/edit/patch hunks, is unpublished, and Desktop must not depend on sibling source or artifacts.

The supplied numbers justify investigation, not assumed wins: 500k many-block first parse ~869 ms is the headline cost; append ~2.6 ms is already good; open-fence append ~42 ms needs phase attribution before any risky fast path.

## Smallest high-value changes

**1. Add workload attribution before optimizing.** Instrument locally, without protocol changes: time `marked` lexing, `healMarkdown`, per-block `remark` parsing, key hashing, and string detachment separately. The existing injectable `parse` in `createMarkdownWorkerParser(parse)` and exported `buildLiveMarkdownBlocks` make this feasible: run with a stub parser to isolate lexing, and with real parsing to isolate remark cost. Benchmark deterministic generated workloads: 500k many-block first parse, append tick over a long stable prefix, 500k open fence append, reference-definition document, ordinary chat-size message, final non-live parse. Report chars, block count, median/p95, Node/Electron versions, commit. Pre-register a ship bar, for example ≥15% median improvement on targeted workloads and no >5% regression elsewhere; below that, keep `marked.lexer` for simplicity.

**2. Replace `marked.lexer` with block-only lexing, conditionally.** In `buildLiveMarkdownBlocks`, only `token.type` and `token.raw` are consumed; inline token arrays are discarded, and remark re-parses inline content. If the pinned `marked` version publicly exposes a block-token entry point reachable with the exact same options/extensions as the app's configured `marked` instance, use it and skip draining the inline queue. Conditions:

- Construct fresh lexer state per call. Do not reuse an instance across slices: link definitions, `state.top`, in-link/in-raw state, and the inline queue would leak between the stable-prefix slice and later appends, and an undrained queue is also a memory leak.
- Replicate `marked.lexer` entry semantics exactly. Do not add your own CRLF normalization, tab expansion, or pedantic trimming. Current `stablePrefixLength` arithmetic sums `token.raw.length` against the original string's code units; any normalization difference silently misaligns the slice boundary on the next tick. The target is a `[type, raw]` sequence identical to `marked.lexer` for the same input slice, including CRLF, lone CR, tabs, and surrogate pairs.
- Keep the call inside the existing `try/catch` so lexer failure still falls back to one whole live block.
- If block tokens are only reachable via private internals, or the same configured options cannot be supplied, **reject this change** rather than forking or copying marked's tokenizer.

**3. Two measured micro-candidates, only if attribution indicts them.** `hasOpenFence` currently does `trimEnd().split("\n")` over the whole live code block per tick; replacing it with a last-line scan via `lastIndexOf("\n")` is semantically testable and low risk. Separately, the `split("").join("")` detachment in the worker parser runs on every full block, including non-live final parses where the worker retains nothing; consider detaching only blocks that will actually be retained as stable, but only with a memory-retention check, since that copy exists to defeat V8 sliced-string retention. Neither should ship on intuition.

## Explicitly rejected

**Batching small stable blocks for remark: reject now.** Remark parsing is block-local today, and positions in each tree are relative to that block's source. Joining blocks changes semantics before it saves time: remark could merge or reinterpret constructs across the seam — lazy paragraph continuation, setext headings, reference and footnote definitions, HTML blocks, math, tables, list looseness — and splitting a combined tree back into per-block trees requires provenance tracking plus offset remapping on every node. The protocol still returns one tree per block, so batching adds a mapping layer for an unproven saving. Revisit only if attribution shows per-call remark overhead, not tokenization, dominates, and then only for a narrow proven class with full tree equality.

**Handwritten open-fence fast path: reject now.** A correct scanner must reproduce marked/CommonMark behavior for up to three leading spaces, tab expansion, backtick fences whose info string contains backticks, tilde fences, closing fences at least as long as the opener with only trailing blanks, CRLF, EOF without a closer, and fences nested in blockquotes or lists. Worse, the fence block is the live tail, so it is never in the stable prefix; and remark still re-parses the entire growing code block every tick, so lexing may not be the 42 ms. A conservative incremental variant — cache open-fence state and fully re-lex if the appended chunk contains any candidate closing line — changes the cache shape and is a second project. Defer until attribution separates lex, remark, and structured-clone costs for that workload.

**No WASM work.** The prior probes show Shiki WASM is not consistently faster than JS, and the diff pilot lacks the required surface. Both stay out.

## Regression tests that matter

- **Token golden parity:** for a corpus, assert the new lexing path yields the same `[type, raw]` sequence as `marked.lexer`. Corpus: CRLF and lone CR, tabs before fences/lists, multi-line reference destinations, footnotes, tables, setext, thematic breaks, HTML comments, nested blockquote/list, open and closed fences with longer/shorter closers and info strings, math, trailing whitespace, empty and space-only input, unpaired surrogates.
- **Append-sequence parity:** extend the existing character-by-character pattern — parse every prefix of documents built from fragments that change block interpretation only when completed, asserting `toEqual(parseMarkdownInWorker(...))` at each step, as the current reference-definition, table, math, and fence tests already do.
- **Reference boundary cases:** definition split across the stable/live boundary, definition completed by the final appended character, definition inside the re-lexed tail only.
- **Fence `hasOpenFence` equivalence**, if that micro-change ships: fuzz against the current implementation over trailing blank lines, `\r`, trailing spaces/tabs, shorter closers, closers with info text.
- **Bounded failure:** deeply nested blockquotes/lists and pathological bracket input must terminate within a test timeout and return the whole-live fallback rather than throwing or hanging; assert shape, not engine-specific error classes.
- **Responder invariants:** existing owner/revision/finalization and reference-invalidation tests must pass unchanged — no protocol, ownership, or cache-shape changes are in scope.

## Verification gates

Unit parity proves semantics; Node benchmarks prove speed only locally. Because the existing Electron renderer trace uses an isolated fixture, final acceptance needs a fresh Electron run against the real chat surface: streamed rendering of the corpus workloads, DOM/screenshot confirmation that output is visually unchanged, and trace timings from that environment. Do not claim a UI win from Node numbers alone.
