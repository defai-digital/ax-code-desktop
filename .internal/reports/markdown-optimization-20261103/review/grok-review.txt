The scope is right. Shiki stays on JavaScript because no WASM migration qualified. The private `ax-code-diff` pilot only does duplicate comparison, so leaving it out of diff preview and hunks is correct. The patch stays inside the three intended edits: skip marked’s inline lex, put the incremental cache in lexer coordinates, and read the last fence line without splitting the block.

**Inline lex.** `new marked.Lexer().blockTokens(...)` is the block phase that `Lexer.lex` runs after newline normalization. A new lexer each call keeps the undrained inline queue on that object, so it cannot affect the next tick. This file only reads `type` and `raw`; remark parses inline syntax later. Block `raw` is fixed before inline tokens are filled, so skipping that drain does not move block boundaries. The `inlineTokens` spy matches the current marked 17 behavior.

**CRLF coordinates.** `/\r\n?/g` → `\n` matches `Lexer.lex` (`\r\n` or a lone `\r`). The cache stores that normalized string, and `stablePrefixLength` is a sum of token `raw` lengths in the same space. Append-only updates stay prefix-stable, including a `\r` at the end of one chunk and `\n` at the start of the next: `\r` and `\r\n` both become one `\n`, so the new normalized text still starts with the cached text. Re-lexing `normalizedText.slice(stablePrefixLength)` cannot repeat a completed block because of a longer CRLF prefix. An older in-memory cache that still holds CRLF fails `startsWith` and is re-lexed from scratch.

**Fence line.** After `trimEnd()`, `lastIndexOf("\n")` plus `slice` is the same last line as `split("\n").at(-1)`, including a string with no newline (`lastIndexOf` is `-1`, so `slice(0)` is the whole line). `.trim()` and the closer regex are unchanged.

**Failure and reference-definition paths.** Both still return one whole-text block and `emptyCache` on the original string. Reuse requires `stablePrefixLength > 0`, so that un-normalized cache is not sliced in the normalized coordinate space. A later successful lex simply starts over. Malformed input that throws inside `blockTokens` still hits that fallback.

The new tests cover the real risks: normalized offsets with reused block identity, `\n` / `\r\n` / `\r` raws against `marked.lexer`, a CRLF pair split across chunks, and the inline spy. Three pre-fix failures and 59 passing focused tests fit that picture.

Do not treat this as a measured speedup. The chat parser is still dominated by remark; the win here is removing a second inline tokenization and correcting cache coordinates.

Watch items only, not fixes: the spy is tied to `Lexer.prototype.inlineTokens`, so a future marked that inlines through another method could do extra work while the test stays green; whole-block fallback raw can still contain CRLF while lexed blocks are LF, which is the same split `marked.lexer` already had.
