# SDK 2.6.13 integration and Desktop Rust hotpath review

Date: 2026-10-13
Reviewed Desktop baseline: `91322d15473841a1285ff15ed4eb3a577999ae3e`

## Outcome

Update the published SDK from 2.6.12 to 2.6.13. Session operations, authenticated
startup, scoped headers, SSE framing, cursor reconnect, and packaged-origin CORS
passed the checks below. Keep the current production event transport: the Rust
bridge still fails the large-workload latency screen. Embedded browser AI access
has a separate signed-runtime contract gap; the SDK update does not resolve it.

## Integration findings

1. **Embedded AI browser access remains gated by a producer release.** The live
   7.25.1 capability endpoint returns HTTP 200 with `desktop.webmcp.v1`, but no
   `browserMode`. Current Desktop capability and enable checks require
   `browserMode: "embedded"`. The feature therefore stays incompatible. A wrong
   provider token still returns HTTP 403. Tagged 7.25.2 source also omits the
   routing field; source main contains it after those releases. Publish the
   matching producer contract, then repin and qualify Desktop packaging. Retain
   the attestation requirement. See [browser receipt](sdk-2.6.13-integration/browser-capability.json).
2. **Default WS and fallback SDK SSE use different upstream readers.** The
   default path is runtime SSE -> `upstream-reader.js` -> shared global hub ->
   WS -> renderer pipeline. It does not invoke the new SDK SSE parser. The SSE
   fallback uses the published `sdk.global.event`, with SDK retries disabled so
   Desktop owns reconnects and cursors. Dependency installation alone does not
   optimize the default WS upstream reader.
3. **Framing admission and recovery need parity before a transport migration.**
   SDK SSE now caps one event at 16,777,216 buffered UTF-16 units and terminates
   an oversized subscription. Desktop's upstream reader has no explicit partial
   frame size cap, and global replay retains up to 2,048 entries by count rather
   than aggregate bytes. The outer Desktop transport still retries failures, so
   an event over the SDK cap could be replayed repeatedly without dedicated
   oversize recovery. These are source-derived integration gaps, not observed
   user-session failures. Align admission, explicit resync/recovery, unknown
   events, and cursor semantics before adopting a different language. Use public
   SDK APIs or obtain a public parser contract; do not import private dist files.
4. **Existing JS optimizations materially reduce work.** Delta application
   batches clone the part map once per batch and use a last-part lookup fast
   path. The local reducer microbenchmark measured 20 deltas across 8,000 cached
   records at 26.92 ms sequential versus 1.33 ms batched. Turn projection reuse
   measured 0.494 ms full versus 0.226 ms incremental for 500 turns. These are
   CPU microbenchmarks, not user latency or SDK speedup claims. Diff rendering
   already has a worker factory, and streaming code blocks defer Prism work.

## Fresh Rust comparison

The existing isolated experiment was rerun against current Desktop source after
installing SDK 2.6.13. There were 36 Electron runs: one warmup and three measured
rounds for each path and workload, rotating path order. All delivery, revision,
input, and callback assertions passed. Values are medians of measured runs'
publication-to-React-commit p95 on this macOS arm64 host:

| Active projects | Current JS WS | Direct JS IPC | Direct Rust IPC |
| --- | ---: | ---: | ---: |
| 1 | 33.48 ms | 30.88 ms | 29.97 ms |
| 5 | 30.45 ms | 30.50 ms | 33.40 ms |
| 20 | 40.88 ms | 29.91 ms | 71.78 ms |

At 20 projects, direct JS IPC reduced this metric by about 26.9%; it still misses
the experiment's 30% screen. Rust increased it by about 75.6%. The Rust path adds
native JSON parsing, batch serialization to stdout, host JSON parsing, and
Electron structured-clone delivery. These additional boundaries are candidates
for cost reduction; the timing comparison does not isolate their causal share.
Lower measured JS-host CPU does not establish lower total CPU: helper and
renderer CPU are excluded. RSS observations are not peak-memory qualification.

This fixture uses actual Desktop WS bridge/pipeline/reducer code and a React
fixture, with a synthetic SSE producer. It supplies a dummy SDK for the forced
WS path and a fixture-specific adapter for IPC paths. It **does not measure the
new SDK SSE parser**, model latency, real app paint, or production recovery parity.
Full numeric evidence and version context are in
[transport-measurements.json](sdk-2.6.13-integration/transport-measurements.json).

## Migration recommendation

Prioritize fewer copies and boundary crossings. First evaluate a bounded
incremental upstream reader, a byte-bounded ring replay buffer instead of
per-event array splicing, and serialization reuse across WS subscribers. A
direct JS IPC experiment is useful as an architectural control, but needs
notification, replay, reconnect, dedup, and profile/packaging parity before
production adoption.

Consider Rust only for measured CPU-heavy, bounded pure transforms that can keep
their working state native and emit small patches: large-history indexing or
projection, and large markdown/diff parsing where the existing workers still
show measurable cost. Profile each first, compare the current JS/worker control,
and include transfer and renderer costs. None of these additional Rust candidates
was implemented or benchmarked here. Keep React/Zustand updates and DOM work in
the renderer. Repository search, indexing, patch execution, and canonical runtime
state remain AX Code responsibilities; its existing native implementation should
be consumed through its public contract rather than duplicated in Desktop.

The released source still provides a JS/TS SDK and a language-neutral gRPC proto,
not a first-party Rust SDK crate. Existing runtime MsgPack IPC forwards parsed
SSE data without its `id:` metadata. Neither that transport nor a generated Rust
gRPC client is an automatic replacement for Desktop's cursor/recovery contract.
