### P2 findings

**1. An unacknowledged stop survives Disconnect → Enable and refuses every later call until the page is reloaded.**
`native-webmcp.js:531-537`: when `boundedStop` returns `still-finishing`, `pending.reject(..., retain = true)` keeps the entry; `execute` refuses any invoke while `pending.size !== 0` (`:321-322`). `disconnect()`→`revoke()` re-enters `cancel`, which returns the already-stored `pending.stopping` (`:527`) and never clears the entry.
Repro: page tool `async () => { await new Promise((r) => setTimeout(r, 120000)) }`; agent invokes; press Disconnect; press Enable; Try it or let the agent call again → `failed/native-failure` ("Native operation is unavailable") every time. Impact: a documented flow (pause/disconnect then re-enable) silently stops working; no false success is claimed and Reload recovers (it invalidates, and `invalidate` rejects-retained entries at `:138-141`), so P2 not P1. Fix: in `disconnect()`, drop retained entries whose `stopping` promise has already settled, or clear `pending` on a fresh enrollment.

**2. An eviction refusal surfaces as a generic start failure instead of the documented pool-full state.**
`desktop-webmcp-browser.js:147-148`: `unload()` probes `closeForEviction`, then calls `close(entry)`, which probes again (`:429-431`) and throws "Browser page refused closure". The throw escapes the candidate loop (`:825`) and rejects the whole `create`.
Repro: 4 live views; ask for a 5th; the least-recently-used page installs a `beforeunload` after the first probe (a timer, or an input/visibility listener installed from page script). The pane's catch matches only `"pool-full"` (`EmbeddedWebMcpBrowser.tsx:265`), so `poolFull` stays false and the person sees `start-failed` + Reopen, while `docs/webmcp-page-tools.md:132-133` promises a named list of retained pages. Impact: recovery guidance lost; no data loss. Fix: catch the refusal inside the loop and `continue` to the next candidate, ending with `pool-full`.

**3. A pop-out reservation can outlive a failed open when the window inventory call also fails.**
`sessionGridPopout.ts:57-76`: the slot is marked popped and the key enters `owners` before `openSessionWindow`; only `reconcileGridWindows()` clears it, and its failure is swallowed (`:36-38`). Because `SessionGrid.tsx:288` renders `WebMcpSessionPage` only when `!popped`, a slot in that state has neither an in-grid browser nor a window. Impact: one grid slot shows a popped state with no owner until the next successful reconcile (focus / `session-windows-changed`), i.e. self-healing, hence P2. Fix: on a false/throwing open, remove the reserved key from `owners` directly rather than relying on the inventory.
