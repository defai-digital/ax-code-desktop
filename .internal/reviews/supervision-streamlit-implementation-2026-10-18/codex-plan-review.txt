The scope is sound based on the supplied excerpts. Before implementation, tighten the following contracts; the main risks are stale reconciliation, request identity drift, and confusing preview navigation with process readiness.

1. **Define successful replies as terminal for submission.**

   In `RequestActionCard.tsx:51–65`, `finally` currently unlocks the card after every outcome. Replace that behavior with explicit states:

   - Sending: disable all decision controls.
   - Successful SDK reply: show “Response accepted; updating…” and keep decisions disabled until canonical removal.
   - Failed reply: reconcile before enabling another decision.
   - Successful reconciliation: pending permits explicit retry; absent means “No longer pending.”
   - Failed reconciliation: remain uncertain, with “Check status” and “Open session.”

   Success must not depend on SSE arrival. SSE removes the presentation; it does not determine whether an acknowledged reply succeeded. A delayed SSE must never enable resubmission. Keep the live status mounted and announce changes politely without moving focus.

2. **Bind submission and reconciliation to the same request provenance.**

   The current `requestKey` excludes client and directory. Meanwhile, `respondToPermission` resolves routing **after** `waitForConnectionOrThrow()`. The excerpts do not establish whether its helpers preserve the originating connection across a project or connection switch.

   Capture an immutable operation identity covering client/connection generation, directory, session, kind, and request ID. Verify that both the reply and pending-list read use that identity; fail visibly if its original scope is unavailable.

   A mounted flag alone is insufficient. Every asynchronous completion—including `finally`, error presentation, and reconciliation—must check operation identity before changing state or releasing a lock.

   Also verify whether multiple surfaces can render the same actionable request simultaneously. If so, use a small shared operation record in the existing state layer so another card or remount cannot bypass the pending/accepted lock. This is local duplicate suppression, not an exactly-once runtime guarantee.

3. **Make reconciliation observation-only and resistant to stale reads.**

   Do not call `resyncBlockingRequestsForDirectory`. Use the scoped SDK list operation without invoking auto-accept behavior or replacing the canonical pending collection.

   A request is absent only after a successful, valid, complete response for its original scope, filtered by session, request kind, and request ID. SDK errors, malformed responses, and unavailable scope must remain uncertain—not become an empty list.

   Capture a local observation revision when the read starts. If a relevant canonical event or identity change occurs before completion, discard the stale result. In particular, an old “pending” response must not re-enable a request already resolved through SSE.

   A pending observation permits an explicit retry but does not prove the original write cannot still finish. Preserve that distinction in copy and tests; avoid automatic retries or claims of guaranteed non-delivery. Use generic localized errors instead of `error.message`.

4. **Specify preview lifetime and bounded connection recovery before P4.**

   `ProjectActionsButton.tsx:614–633` opens the URL before sending the command. Moving navigation after successful `sendInput` is necessary, but input delivery is still not server readiness.

   Associate initial connection recovery with the action run, project, tab, URL, and navigation generation. Use a concrete total deadline—for example, 30 seconds—with bounded retries for initial main-frame connection failures. On timeout, show a stable failure state with explicit Retry/Open externally controls.

   Navigation, unmount, or replacement runs must cancel obsolete retries and listeners. Cancellation must not stop the terminal-owned process or reopen a preview the user left. A manually opened URL owns no process.

   Define hide/remount behavior explicitly: a persistent browser profile does not establish Streamlit session continuity. Preserve existing preview lifetime semantics and document observed reconnect behavior.

   A port collision must surface as a launch failure rather than presenting the existing occupant as the newly launched app.

5. **Treat interpreter and entrypoint as structured values, not shell fragments.**

   `stripControlChars` is not shell escaping. Generated recipes need a serializer appropriate to the actual terminal shell. Prefer existing argument-based execution if available; otherwise explicitly support and test known shell dialects rather than introducing a new launcher.

   Store interpreter and entrypoint as unquoted paths. Resolve the working directory deliberately, reject embedded control characters, validate the port, and quote each generated argument exactly once. A POSIX quoting helper cannot establish PowerShell or `cmd.exe` safety.

   Acceptance tests should round-trip paths containing spaces, Unicode, quotes, and shell metacharacters without executing additional commands. Unsupported shells should produce a clear limitation.

6. **Make the evidence gates concrete and small.**

   For P0, record Electron zoom, measured CSS viewport, window dimensions, and device scale factor. Exercise all three widths at normal and doubled zoom using real components, long content, expanded scopes, and representative long translations. Pass when decision controls and status remain reachable, focus is visible, and keyboard activation cannot submit conflicting decisions.

   For P3, record exact fixture dependencies and platform versions. Core compatibility requires widget/form round trips, multiple streaming updates, reload/reconnect, server restart, and correct routing across two projects. Record upload/download content round trips separately; explicit external fallback is partial compatibility, not native success.

   Exercise the unchanged webview policy. The shared partition is not a per-project isolation boundary; include same-host cookie interactions in the two-port fixture. Clearly distinguish native fixture qualification from full application E2E.

Keep P4 as one reusable Project Actions recipe using existing terminal ownership and ordinary preview. Defer generalized discovery and readiness infrastructure unless the spike demonstrates a concrete need.
