Lifecycle hooks are a narrow runtime control, not a Desktop feature that has earned a top-level Settings page. Keep a reduced runtime mechanism. Demote the page until project identity is unambiguous and one blockable job changes outcomes beyond permissions.

**Keep the mechanism.** It is the only described way to run user shell on a tool or Stop boundary and veto a defined blockable event before the call proceeds. Permissions, notifications, and the scheduler do not do that. Trust stays off unless set outside repository config, which limits repo-supplied commands. Jobs worth that power: block a named read or write of env or secret files; deny a specified tool pattern; on Stop, return model-visible feedback that a required check was not recorded. A recap can cite that trace. Value exists only when the veto or feedback changes the next action.

**Reduce the page and the extra surface.** The Settings page is read-only: trust, validity, path, effective event, matcher, command, source, packs, refresh, and open file. It does not edit, enable, or run hooks. Same-name project options make that inspection unsafe, because trust is per project. Packs such as format-after-edit and require-tests-on-stop are reminders, so a prominent page can imply evidence they do not provide. Observation-only events cannot veto, still use the four-process cap, and have no exactly-once or general security guarantee. Commands stay unsandboxed. AX Agent owns future durable orchestration; AX Trust owns enterprise policy. Hooks must not become a second scheduler or a recurring spend loop.

**Non-goals.** A general security product, exactly-once delivery, proof of format or tests, WebMCP, in-UI authoring, automatic recurring runs, and enterprise policy distribution.

**Priorities.** Finish and validate project-identity repairs before Hooks is a Settings destination. Keep runtime support for blockable vetoes and model-visible feedback, with timeout, output bounds, environment sanitization, and the concurrency cap. Move the page to an advanced per-project inspector showing which command can block which event, plus open file. Do not add enable, edit, run, or packs that imply verification.

**Hide or remove.** Hide the page while project identity is ambiguous, or if a measured window finds no trusted blockable hook and page opens do not lead to an explicit trust action. Remove the runtime feature if traces show vetoes add nothing beyond canonical permission decisions, or unsandboxed-command failures outnumber successful vetoes. Missing adoption data is not proof of value or of waste.

**Validation.** For a fixed window, record trusted projects, blockable versus observation hooks, vetoes, model turns quoting hook feedback, added latency, timeouts, cap saturation, wrong-project opens, and support contacts. Mechanism pass: a PreToolUse veto stops the named call, and a Stop hook changes the next model action versus the same task with hooks off. Fail if the call or stop still proceeds, or the user cannot name the project. Page pass: from the UI alone, the user can state event, command, source, and project path, with no duplicate controls. Otherwise the page stays hidden.
