**Recommendation: Method B (deterministic, project-aware run), with A deferred as a thin convenience over B's primitives, not a substitute.**

**Method comparison**

- **A (natural-language agent):** Pros — zero new UI, reuses canonical agent. Cons — requires an agent-to-persistent-terminal API that is explicitly unverified; execution is non-deterministic, slow, token-costly; "least learning curve" fails because users must learn to prompt an agent and audit its shell. Cannot be the reliable repeat-run path today.
- **B (project-aware deterministic run):** Pros — one or zero user decisions per app; respects existing venv/uv conventions; repeat runs are byte-identical commands in a visible terminal; all infrastructure (terminal, preview, free-port) already exists. Cons — needs detection logic and honest failure UX.
- **C (uv ephemeral `--with streamlit`):** Pros — works with no project setup. Cons — per-run environment resolution (network-dependent, slow), `--with` can silently conflict with project deps, nothing persists, and it teaches users that environments are disposable. Wrong for maintained projects; acceptable only as an explicit "throwaway experiment" escape hatch.
- **D (Docker/hosted):** Pros — perfect reproducibility for teams. Cons — highest learning curve and setup cost (Docker install, image, ports, volumes); a new service dependency; violates "prefer existing infrastructure."

**Normal-user story:** User opens a Streamlit project, clicks **Start**. Detected `venv` → runs `<venv>/bin/python -m streamlit run app.py` in a visible terminal; preview attaches. Missing deps → one dialog: "Install into this project's `.venv` from `requirements.txt`? [Setup and run] [Cancel]." One click, done forever. Ambiguous entrypoint (`app.py` vs `streamlit_app.py`) → one picker, remembered in the recipe.

**Automatic vs explicit:** Automatic — entrypoint candidates by convention (root `app.py`, `streamlit_app.py`, `src/`; never router/helper modules), port via `/api/system/free-port`, localhost/headless bind, terminal/preview lifecycle, error surfacing from real command output. Explicit — any dependency installation, lockfile rewriting, entrypoint choice when ambiguous, environment creation when none exists. Never automatic on project open.

**Dependency/lock/ownership rules:** Existing `.venv` is reused untouched. `pyproject`+`uv.lock` → `uv run --locked`; on stale-lock failure, show the real uv error and offer explicit `uv sync` — never auto-rewrite the lock. `requirements.txt` only → install into the project-isolated venv only after confirmation. No uv binary → same flow with `python -m venv` + pip, still project-isolated; no global install, ever. Process stop targets only the tracked terminal's command. Quick experiments: users may hand-edit the recipe (C is available as a typed command) without B endorsing it.

**Smallest v3 to ship now:** (1) detection layer picking the command from venv/uv.lock/requirements/presence of uv, with the resolved command shown before execution; (2) one **Setup and run** action behind the confirmation dialog; (3) real stderr in the action result instead of generic errors; (4) keep Add/Save/Start but make Start work without prior Save for detected projects. No new services, no agent dependency.

**Rejected from prior discussion:** the Qwen/MiniMax "copyable pip command" advice. It shifts environment work to the user — exactly what "least human effort" forbids. Install must be executed by the product, explicitly confirmed, project-isolated.

Offline: `--locked`/cached-venv runs still work; install actions must fail with a clear "network required" message, not hang.
